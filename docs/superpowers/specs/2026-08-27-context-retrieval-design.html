Uploaded-document context retrieval

Let a team upload documents and have an agent automatically receive the parts relevant to the task it was given — retrieved per run, budget-capped, and visible after the fact.

Date 2026-08-27 Status Approved Commit 7c36043 Sequence 7 PRs
Problem Ground truth Scope Design decisions Mechanism Testing PR sequence Risks

Problem

A team's knowledge lives in documents — specs, handbooks, runbooks, design notes — and none of it can reach an agent today. teams.shared_context is the only path, and it is deliberately the wrong shape for this: 64 KB, always injected into every prompt, hand-typed into a textarea.

The intended second half of that design — ARCHITECTURE.md §2.3's "shared_context = small, hot, always injected; context_items = large, cold, retrieved" — does not exist. team_context_items holds id, team_id, title, size_bytes, created_at and nothing else. There is no file content anywhere in the system: no blob store, no S3, no bytea. POST /api/teams/[teamId]/context-items accepts a JSON title and a claimed sizeBytes, and a repo-wide grep shows zero callers. It is a metadata stub for a feature that was never built, and the seed populates three rows describing files that do not exist.

Goal

Documents a team uploads reach the agent as retrieved excerpts, chosen per run against the task at hand, capped by a byte budget, and inspectable afterwards — without any of it passing through the always-injected shared_context layer.

Ground truth this design relies on

Every claim below was verified against the repo or against a running container. The two filled markers are deliberate deviations from ARCHITECTURE.md.

  • The platform, not the SDK, composes the prompt, and layers are already first-class. composeSystemPrompt returns PromptSegment[] alongside the joined string, with the invariant that joining the segments reproduces exactly what the model received. runs.prompt_segments persists it.
  • PromptOmissionReason is a closed union in core, but adding a code is explicitly non-breaking — RunContextPanel maps ids and reasons through two lookup tables with a generic fallback for unknown values.
  • Everything retrieval needs is already in scope at the composition call site. worker.ts has team, task, triggeringMessage, and agent loaded before composeSystemPrompt is called.
  • The repo map is the precedent for a machine-generated, budget-capped, injected layer that fails soft — a 16 KB cap enforced at three layers, failure degrading to "" plus an omission reason, and an explicit untrusted-content wrapper because the text comes from an agent reading an arbitrary repo.
  • postgres:16-alpine cannot run CREATE EXTENSION vector at all. Against the running container: ERROR: extension "vector" is not available. There is no out-of-band workaround; the image change is the fix. pgvector/pgvector:pg16 was run and verified: PostgreSQL 16.15, pgvector 0.8.6, superuser role.
  • Drizzle 0.45.2 already has native pgvector support, verified by generating and applying real migrations — the vector(384) column and the HNSW opclass both survive generate intact.
  • drizzle-kit never emits CREATE EXTENSION, but there is a sanctioned escape hatch: generate --custom writes an empty, journalled migration for hand-written SQL, and a later normal generate diffs correctly from its snapshot.
  • The extension migration and the image swap cannot be separate PRs. The db-integration harness runs migrate() in beforeAll, and CI runs db:migrate before e2e. Three image references across two files.
  • The repo has never opened a database transaction. Zero hits for db.transaction(, and the client is a pooled postgres() with no max — a bare SET would land on an arbitrary connection and leak.
  • Next.js 16 Route Handlers have no request body size limit. bodySizeLimit is enforced only on the Server Actions path. No middleware, no proxy. request.formData() is unbounded and buffers the whole body into memory.
  • apiFetch is JSON-only and cannot be bypassed at the call site — it spreads the JSON content-type into a plain object, so the key cannot be removed by passing undefined.
  • The existing context-items routes are not org-scoped. GET/POST call through on an attacker-supplied teamId behind only an auth check, while the sibling delete path does scope. team_context_items has no org_id of its own.
  • agents.team_id is settable across orgs today. The PATCH route is unscoped by acknowledged design debt, updateAgent writes teamId unchecked, and getTeam has no org filter — so an agent in org A can already point at a team in org B and have that team's shared_context injected into a prompt its owner controls end to end.
  • capSharedContext is a live byte-test/character-slice bug. A 40 000-character string of 3-byte codepoints measures 120 000 bytes, survives slice(0, 65536) unchanged, then violates the octet_length CHECK — a 500, not a 400. Precedent to avoid, not to copy.
  • pnpm-workspace.yaml uses an explicit allowBuilds allowlist. onnxruntime-node's postinstall fetches its native binding; unlisted, it installs silently and fails at the first inference call.
  • The worker runs on the host via tsx watch; the only Dockerfile is the sandbox image. All four BullMQ Workers register with { connection } alone — concurrency 1, no attempts/backoff anywhere, no SIGTERM handler.
  • The unit test project has no database and no Redis, and .husky/pre-push runs it. packages/queue throws at import when REDIS_URL is unset.
  • The e2e suite stubs nothing. It seeds through the app's own HTTP API and asserts real responses, and no worker runs during e2e. Grading quality is explicitly not asserted in CI.
  • pgvector stores real (float32). 0.8414709848078965 reads back as 0.84147096.
  • Deviation — the vector is 384 dimensions, not ARCHITECTURE.md §2.4's 1536. The doc's number assumed an OpenAI model; the dimension follows the chosen embedder.
  • Deviation — the retrieved layer sits before team_context, not after (§3). Argued under Design decisions.

Scope and non-scope

Touched

  • docker-compose.yml, .github/workflows/test.yml (×2) — Postgres image → pgvector/pgvector:pg16.
  • pnpm-workspace.yaml — allowBuilds: onnxruntime-node: true.
  • packages/db — a --custom extension migration, then generated migrations for content_blobs, the team_context_items columns, context_chunks, run_context_retrievals; four new repositories plus an org-scoped getTeamForOrg; seed and test-harness updates.
  • packages/storage (new) — BlobStore port, FsBlobStore, S3BlobStore.
  • packages/core — TeamContextItem fields, ContextItemStatus, three new PromptOmissionReason codes, RunContextRetrieval.
  • packages/queue — the context-ingest queue and its enqueue function.
  • apps/worker — embedder, text-extract, chunker, context-ingest, context-retrieval (all new), plus prompt-composition.ts and worker.ts.
  • apps/web — the context-items routes, a new GET /api/runs/[runId]/retrievals, api-client.ts, the team page, a new ContextDocumentsPanel, RunContextPanel, and en.ts.
  • Both .env.example files and README setup — BLOB_STORE / BLOB_DIR, the same value in each.

Explicitly out

  • Connectors (Drive, Notion, Monday, URLs). source is added and always 'upload'; other sources become adapters later.
  • PDF and .docx. Ingestion accepts text/markdown and text/plain only. TextExtractor is a seam from day one precisely so each format is a later, isolated PR.
  • Manual pinning, per-agent toggles, and user-tunable k/floor. The right defaults are not known yet; tuning waits on the PR 7 numbers.
  • A search_context agent tool. This layer is pre-injected text, like the repo map — the agent has no awareness a retrieval step exists.
  • Re-embedding on a model change. The embedding_model stamp makes a mixed state detectable; the backfill command that acts on it is not built here.
  • Blob garbage collection. Deleting an item leaves its blob; blobs may be shared between items within an org, and nothing reclaims them yet.
  • Fixing capSharedContext, and fixing the unscoped agents PATCH route. Named as precedent and as context, not repaired here.

Design decisions

Embedding

  • A local embedding model is the default in dev and production, behind an Embedder port. bge-small-en-v1.5 via @huggingface/transformers, 384 dimensions, no API key, no per-token cost, no data leaving the host. The alternative — local in dev, hosted in prod — was rejected outright: a pgvector column is typed with a fixed dimension and an HNSW index needs that dimension, so two environments would mean two schemas and a dev setup that never exercises the production retrieval path.
  • Queries are embedded with the model's instruction prefix, documents are not. bge-* is asymmetric. Getting this wrong costs real retrieval quality and is invisible without evals, so it belongs in the Embedder contract (embedQuery vs embedDocuments), not at call sites.
  • The embedder is an injected dependency, lazily initialised, cached at module scope. .husky/pre-push runs test:unit — a module-scope pipeline() would make the first push after a clone download a model from the hub. Lazy init also protects tsx watch, which would otherwise reload the model on every save.
  • Embedding runs in batches with yields between them. The ingest worker shares a process with the run worker at concurrency 1. Batches of 32 bound the damage. A known tradeoff, not a solved problem — if ingest latency starts delaying runs, the fix is a separate process, driven by measurement.

Retrieval

Measured, not assumed

HNSW plus a tenant filter silently under-returns. On a realistic table (5 teams × 2 000 chunks, 384-dim, analyzed), the exact query shape this design needs returned 4 rows out of a requested 10:

Limit (actual rows=4 loops=1)
  ->  Index Scan using cc_hnsw on cc (actual rows=4 loops=1)
        Filter: (team_id = 3)
        Rows Removed by Filter: 36

hnsw.ef_search defaults to 40, the index yields ~40 candidates globally, and the tenant filter applies afterwards. A similarity floor does not rescue it — it becomes another post-index filter. SET LOCAL hnsw.iterative_scan = relaxed_order returned the full 10.

  • The HNSW index ships, and every retrieval query runs inside a transaction with SET LOCAL hnsw.iterative_scan = 'relaxed_order'. Without it the layer silently degrades in a way no error surfaces. SET LOCAL requires a transaction because the client is pooled. Because relaxed_order may return candidates slightly out of order, the top-k select is wrapped in a subquery with an outer ORDER BY so the persisted rank is deterministic. A db-integration test asserting "k eligible chunks ⇒ exactly k rows" is the regression guard.
  • A similarity floor, not just top-k. Top-k alone always returns something; with no relevant documents that something is noise injected into every prompt, which is exactly how context pollution starts. Below the floor the layer is omitted entirely.
  • The byte budget is enforced by dropping whole chunks, never by slicing text. Measured with TextEncoder().encode(...).length, accumulated chunk by chunk. A half-sentence adds nothing, and String.slice on a byte budget is the capSharedContext bug.
  • Retrieval never fails a run. Any error — embedder unavailable, query timeout, extension missing — degrades to an omitted segment with a reason and a logged error, exactly as ensureRepoMap returns "".

Tenancy and safety

  • Retrieval resolves the team org-scoped, because agents.team_id is attacker-settable across orgs. For shared_context that leaks one fixed 64 KB blob; a retrieval layer over it would be a repeatable query interface over an arbitrary corpus, since the query is built from the attacker's own task text. So this design does not inherit the gap: the worker replaces getTeam with getTeamForOrg, a cross-org pointer yields undefined, the layer is omitted under the existing no_team reason, and the pre-existing shared_context leak closes on the same line.
  • Blobs are partitioned by org: the key is (org_id, sha256), not sha256 alone. A bare content key partitions nothing. Two orgs uploading the same bytes contend for one row, and every conflict action is wrong: DO NOTHING leaves org B's item pointing at a row org A owns, DO UPDATE silently transfers ownership, and deleting org A then cascades that row out from under org B's still-referencing item. Cross-org dedup of files capped at 2 MB of text saves nothing worth that.
  • The unscoped context-items routes are fixed in this work, not left for later. Once those rows become chunks injected into another org's prompts, an unscoped write stops being a data-integrity bug and becomes cross-tenant prompt injection.
  • Retrieved text is wrapped and labelled as untrusted reference material. Uploaded documents are the most directly attacker-controllable text in the whole prompt.
  • Upload size is capped by the route, and Content-Length is a gate, not the cap. The header is client-supplied and absent entirely under chunked encoding, so the rule is "no trustworthy declared length ⇒ no upload": missing or unparseable is a 413, not a pass, because request.formData() would otherwise buffer an unbounded body into the single web process that serves every org.
  • Duplicate uploads are rejected, not deduplicated into two items. A unique index on (team_id, sha256) returns 409 — two items over one blob would both match retrieval and spend the budget twice on identical text.

Plumbing

  • apiFetch gains a FormData branch rather than being bypassed. "One call site for all client→API traffic" is a stated invariant of that file; an upload calling raw fetch quietly ends it.
  • Ingestion retries; runs do not. The no-retry rule exists because a run may already have pushed a commit or commented on a PR. Ingestion touches nothing outside our own tables and is idempotent, so attempts: 3 is safe — this is the first retry configuration in the repo, so PR 4 introduces the pattern rather than following one.
  • A crashed ingest is recoverable by design rather than by a shutdown handler. There is no SIGTERM handling in this process; instead the job is idempotent and indexing is an accepted entry state, so a stalled redelivery re-runs cleanly.
  • What was retrieved gets its own table, served by a lazy route. RUN_COLUMNS exists to keep large per-run blobs off a 1.5 s poll.
  • Provenance survives document deletion. run_context_retrievals stores an item_title snapshot and nulls item_id on delete. The retrieved text itself is already preserved verbatim in runs.prompt_segments.
  • The three placeholder rows leave the seed. They describe files that do not exist and cannot be ingested; with a real documents list rendering status, they would sit at pending forever.

Mechanism

Schema

export const contentBlobs = pgTable("content_blobs", {
  sha256:    text("sha256").notNull(),
  orgId:     integer("org_id").notNull().references(() => orgs.id, { onDelete: "cascade" }),
  sizeBytes: integer("size_bytes").notNull(),
  mime:      text("mime").notNull(),
  createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
}, (t) => [primaryKey({ columns: [t.orgId, t.sha256] })]);

export const contextChunks = pgTable("context_chunks", {
  id:     integer("id").primaryKey().generatedByDefaultAsIdentity(),
  itemId: integer("item_id").notNull().references(() => teamContextItems.id, { onDelete: "cascade" }),
  // Denormalized from the item: retrieval always filters on it, and a filtered
  // HNSW scan wants the predicate on the indexed table rather than behind a join.
  teamId:   integer("team_id").notNull().references(() => teams.id, { onDelete: "cascade" }),
  chunkIdx: integer("chunk_idx").notNull(),
  text:     text("text").notNull(),
  embedding:      vector("embedding", { dimensions: 384 }).notNull(),
  embeddingModel: text("embedding_model").notNull(),
}, (t) => [
  index("context_chunks_embedding_idx").using("hnsw", t.embedding.op("vector_cosine_ops")),
  index("context_chunks_team_id_idx").on(t.teamId),
]);

team_context_items gains org_id, sha256, mime, source, status, error, indexed_at, uploaded_by, a composite FK to content_blobs, and a unique index on (team_id, sha256). run_context_retrievals mirrors run_evals: own table, run_id index, item_title snapshot, rank, score.

Migration order: db:generate --custom --name enable_pgvector → paste CREATE EXTENSION IF NOT EXISTS vector; → db:generate for the tables. The new NOT NULL columns require an empty table, which it always is — nothing has ever written to it outside the seed — so PR 2 leads with a second --custom migration clearing the placeholder rows.

Blob storage

export interface BlobStore {
  put(orgId: number, bytes: Uint8Array, mime: string): Promise<{ sha256: string; sizeBytes: number }>;
  get(orgId: number, sha256: string): Promise<Uint8Array | undefined>;
}

FsBlobStore writes <root>/<orgId>/<sha[0:2]>/<sha>; S3BlobStore puts at the same key. apps/web writes the blob and apps/worker reads it, as two host processes started from their own package directories — so BLOB_DIR is never resolved against process.cwd(). An absolute value is used as-is; a relative one resolves against the repo root derived from the package's own location, so the same string means the same directory in both processes.

Upload

POST /api/teams/[teamId]/context-items   (multipart/form-data)
  → requireAuthContext, and assert the team belongs to the caller's org
  → reject unless Content-Length parses to a number ≤ 2 MB —
    a missing or NaN value is a 413, not a pass — before touching the body
  → reject a mime outside { text/markdown, text/plain }
  → bytes = await file.arrayBuffer(); re-check size
  → BlobStore.put(orgId, …) → insert content_blobs on conflict (org_id, sha256) do nothing
  → insert team_context_items { orgId, status: 'pending', … }   409 on (team, sha) conflict
  → enqueueContextIngestJob(itemId)   →   201

Ingestion

load item → refuse unless status is 'pending' | 'indexing'   (stalled-redelivery guard)
markIndexing → BlobStore.get → TextExtractor(mime) → chunk()
deleteChunksForItem(itemId)                                  (idempotent re-run)
for each batch of 32: Embedder.embedDocuments(batch) → insert
markIndexed | markFailed(message)

chunk() is pure: split on markdown headings, then ~1 000-character windows with ~150 characters of overlap, each chunk prefixed with <document title> › <heading path>. The prefix is embedded along with the body — a bare paragraph pulled out of a 40-page document is often uninterpretable, and the agent cannot ask where it came from.

Retrieval

query   = [task.title, task.description, triggeringMessage.content].filter(Boolean).join("\n\n")
vector  = Embedder.embedQuery(query)                 // instruction-prefixed
rows    = db.transaction(tx => {
            tx.execute(sql`set local hnsw.iterative_scan = 'relaxed_order'`)
            return tx.select(...)                     // subquery: team filter + <=> order + limit K
                     .orderBy(distance)               // outer re-sort → deterministic rank
          })
kept    = rows.filter(r => 1 - r.distance >= FLOOR)   // FLOOR = 0.35
          .reduce(byteBudget(8192))                   // whole chunks only

K = 12, floor 0.35, budget 8 192 bytes. On success the worker writes run_context_retrievals rows. No run event is emitted — reusing context_included would silently overwrite the shared-context indicator on the task page, which keys that event by runId with last-write-wins.

Platform-authored constraints lead; human-authored instructions go last, with machine-generated reference material before them.

ARCHITECTURE.md §3 puts retrieved items after shared_context, but that ordering predates the measured layer-ordering experiment — 10/10 vs 1/10 on instruction compliance when machine bulk moves ahead of human instructions. Retrieved excerpts are human-written prose but machine-selected bulk, and they are more task-specific than the repo map, so they go after the map and before team context. This ordering is a hypothesis, not a measurement — re-running the experiment once real documents exist is a PR 7 concern.

Three new omission reasons: no_indexed_documents, no_relevant_chunks, retrieval_failed (no_team is reused). An 8 KB layer is small next to the 16 KB repo map, and overflow is already handled by the existing PromptTooLongError escalation path.

UI

Team documents — a ContextDocumentsPanel beside the shared-context panels: drop zone, list of title / size / uploaded-by / status, delete. Polling only while an item is non-terminal.

Run context — the retrieved_context segment additionally renders a provenance group from GET /api/runs/[runId]/retrievals: document title, chunk index, score, expandable text. Unknown ids and reasons already fall back gracefully, so an older client renders the new layer without a core bump.

Testing

  • Unit (no DB, no Redis — this is the pre-push suite). Chunker: heading splits, overlap, an oversized single paragraph, empty file, prefix construction. Byte budget: stops before the chunk that would exceed it, measured in bytes not characters, never slices mid-chunk. Segment builders: each omission reason, and ordering. FsBlobStore: round-trip, SHA determinism, idempotent put within an org. Upload gate: a ReadableStream body carries no Content-Length ⇒ 413 with the blob store never touched.
  • DB integration. Repository lifecycles and org scoping for all four new tables. The filtered-recall guard: k eligible chunks in the team ⇒ exactly k rows — this is the test that fails if the iterative_scan setting is ever dropped. The cross-org retrieval guard: an org A agent pointed at an org B team retrieves zero rows, never an injected excerpt. The blob partitioning guard: two orgs, identical bytes, independent rows. Embedding round-trip asserted with a float32 tolerance, never equality.
  • Component. ContextDocumentsPanel in each status state; RunContextPanel with a retrieved layer present, and with each omission reason.
  • E2E. The suite stubs nothing and runs no worker, so the honest assertions are: upload returns 201 and the document appears with pending; a cross-org teamId is rejected; an oversized upload with an honest header is rejected; a duplicate returns 409. Anything requiring indexed belongs to component and db tests.
  • Not asserted in CI: retrieval quality, following the existing convention for judge quality. PR 7 measures it out-of-band.

PR 3 ends on a gate rather than a deliverable. Everything in PRs 4–7 is plumbing around the assumption that a 384-dimension embedding over 1000-character chunks finds the right passage, and none of those PRs test it — by the time PR 5 could disprove it, four PRs have been built on it. The spike costs an hour, and both levers it can move (the chunk constants, the model id) live in PR 3. If its numbers are bad, the instruction is to stop there rather than start PR 4.

Risks

  • Local embedding quality is only spot-checked before PR 7. PR 3's spike is a gate, not a measurement — ten queries against one corpus. If bge-small proves too weak later, the swap is a vector(N) migration plus a full re-embed — cheap in wall-clock, because originals are kept, but not a config flip.
  • The layer ordering is reasoned, not measured. It follows the rule the ordering experiment established, but that experiment had no retrieved layer in it.
  • Ingest and runs share one process at concurrency 1. Batch yielding bounds the interference; if ingest latency starts delaying runs, the answer is a separate worker process, decided on measurement.
  • hnsw.iterative_scan is load-bearing and invisible when wrong. Its failure mode is fewer chunks, not an error. The db-integration recall test is the only thing standing between a dropped SET LOCAL and quietly degraded context.
