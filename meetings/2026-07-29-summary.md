# Meeting Summary — July 29, 2026

**Participants:** Eran, Or  
**Topic:** AgentFactory — context model, task scoping, onboarding, and UI direction

---

## Key Decisions & Insights

### 1. Three-tier context model
- **Team level** — framing only: team objectives, goals, north star metrics, ownership, structure. *Not* coding standards (too agent-specific). This context applies universally and can be used to challenge off-mission tasks.
- **Agent level** — role definition + code/feature area mapping (e.g., "dependency layer lives in repo XYZ"). Also architecture decisions, PR process, and any persistent reference the agent always needs. This mapping is maintained over time (not one-shot).
- **Task level** — specific context for this task only (Figma links, specific docs, etc.). Both agent-level and task-level context are needed simultaneously.

### 2. Skills bank vs. team standards
Team-level "coding standards" don't make sense universally (a product research agent doesn't need them). Instead, a **skills bank** at the team level — agents are built by selecting relevant skills.

### 3. Task scoping / digestibility
A core product problem: users don't know where the agent's boundary is. Large tasks lead to wasted runs and bad output. The agent should do a **complexity dry-run** and proactively suggest breaking a task into sub-tasks if it's too large (e.g., "this will touch 27 files — want me to split it?").

### 4. Handling unknown context
When triggered on a task it has no context for, the agent must say so explicitly rather than hallucinating a plausible answer. Needs to be enforced in the system prompt.

### 5. Onboarding as a product problem
Good agent quality requires a rich context setup that's hard for users to do manually. Proposed: a **structured onboarding workflow** where the agent asks the user to map repos → team responsibilities → where product docs live, then stores this as the agent's persistent index.

Alternatively (or first): agent does an automated repo scan to generate its own feature/area map, cached for future tasks.

### 6. Task integration
- No intention to replace Jira/Monday — this is an **execution platform**, not a task management system.
- Phase 1: copy-paste from Jira into the agent chat is a valid proof of concept.
- Evolution path: app → Slack → Monday (each has tradeoffs; Slack is more accessible, Monday is more organized).
- Sync integrations are not on the critical path yet.

### 7. UI / Left pane direction
- Tasks displayed as a **sequential table** (not Kanban) — simpler and clearer.
- Single level of sub-tasks (no deep nesting); sub-tasks are created when the agent forks a large task.
- Clicking a pending task → trigger it; clicking an in-progress task → jump to its activity view.
- Agents currently live inside Settings (acknowledged as temporary; needs to move out).
- Agent assignment in the task creation screen is optional, not forced.
